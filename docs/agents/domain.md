# Domain docs

This repo uses a single context with `GLOSSARY.md` at the root and architecture decisions under `docs/adr/`.

Before exploring the codebase, read the glossary and ADRs relevant to the work. If a document is absent, proceed; domain modeling creates new terms and decisions when needed.

Use glossary vocabulary in issues, specs, tests, and code. When a proposed change conflicts with an accepted ADR, name the conflict explicitly and record the superseding decision rather than silently replacing the old rationale.
