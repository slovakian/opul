# Video tools updates and runtime probation

Settings Check for updates resolves the signed runtime pointer and the newest yt-dlp release tag. It persists the last successful check and shows an available version with Update. Both actions use the immediate tools bridge. Ready, installed versions and the current invocation remain available while an update runs; its exclusive flag is the only extra status line. A metadata failure is silent. An installation failure records details in `Tools/updates.log`, retains the committed pair and shows the quiet failed flag.

Setup and updates share signature, checksum, size, archive and health verification. If both components change, the runtime is verified and unpacked before the script is fetched. Every candidate script is tested against the installed runtime, including version, Python deprecation warnings, supported curl_cffi and QuickJS. A newer runtime is then tested with the intended script. An incompatible pair records a hold keyed by script version, the checked runtime number and Opul version. The hold survives restart and avoids fetching that script again until the runtime pointer, script version or Opul version advances. A second integrity failure persists a skip for that component version; newer releases remain eligible. Transient download and activation failures can retry through the next Update operation.

MediaEngine acquires a `VideoToolsUse` from the module when a managed video worker starts executing, after its concurrency wait. Acquisition captures the selected pair and counts usage under the same lock used for activation. Direct transfers and developer overrides do not count. Metadata probes also acquire a usage guard. Runtime unpacking and pair placement wait for managed users to drain, including video Downloads and probes. Network preparation can continue, and further Downloads can use the current pair. After health checks, activation rechecks activity and the original selection, places complete version directories, then atomically commits state.json. Cancellation fences the job before aborting its task and never changes the installed selection. Shutdown cancels the tools operation; Remove also stops and drains media users before deleting tool files through the application state machine.

The previous script is retained until another script update; runtime-only updates leave it alone. A runtime update retains the full last known working pair, even through subsequent script updates, until a video Download using the new runtime succeeds. MediaEngine calls `finish_download` to report success or failure when its process and readers finish. A probe only drops its usage guard, so probe success never clears runtime probation. Cancellation and pause do not count as a failure. The first success clears runtime probation; a preceding failure atomically restores the retained pair. Existing users keep their captured paths until they drain, then unreferenced versions are pruned. Startup also restores the retained pair if the probationary runtime is missing or fails health validation. Ordinary rollback failures remain retryable, while integrity skips apply only to twice-rejected signed downloads. Startup prunes abandoned staging and version directories as before.

A signed runtime that requires a newer Opul is ineligible for installation but does not prevent a compatible script update on the installed runtime. Upgrading Opul rechecks an existing hold even when the runtime pointer is unchanged. Permanent skips are recorded only after the signature or checksum retry is exhausted; ordinary extraction and filesystem failures remain eligible for the next update attempt.

Updater health checks also retain their selected files through a usage guard. A rollback that changes the selected pair invalidates that in-flight candidate before a hold or activation can be committed. Health output that confirms incompatibility can create a hold; process creation, I/O, exit failure and timeout errors leave a retryable failed flag.

## Automatic updates and consent notifications

Opening the video-tools module starts a channel-local scheduler. Only Ready arms its timer. The first deadline is one minute after opening; an overdue deadline runs when setup reaches Ready. Each scheduled attempt establishes the next deadline 24 hours later, including silent failures and checks that find nothing new. Metadata checks fail quietly when offline. They do not leave an offline install waiting indefinitely. Manual checks remain independent of the daily cadence. Shutdown stops the scheduler; Remove cancels the current operation and disarms checks until tools are Ready again.

The injected `NetworkEnvironment` supplies time and cancellable sleeps as well as reachability. Scheduled checks resolve metadata once, then enter the existing verified update path if Keep video tools up to date is enabled. The preference covers both components, is saved immediately, and is read after metadata resolution. Switching it off also revokes a pending automatic install, keeping the selected pair. Turning it on with an available candidate starts an automatic attempt. Explicit Update is consent for that attempt regardless of the preference.

`Tools/state.json` retains the available candidate and notification identities. An identity names the target runtime and yt-dlp versions, so runtime-only releases can notify too. `take_update_notice` atomically persists a claim before returning a short notice. Concurrent consumers, repeated checks and app restarts cannot claim the same candidate twice. Notification history survives Remove. A crash after claiming but before display can lose that toast; Settings retains the available marker and action. This favors the promised absence of repeated notifications.

The frontend shows consent notices only with automatic installation off. Update uses the immediate tools bridge and progress appears only in Settings. Ready's `update_available` projection keeps the marker and action through ordinary install failures, clears them while installing or after success, and excludes compatibility holds and integrity-skipped candidates. The application actor carries this live fact in its runtime overlay. Its Download projection offers Update only for failed tool-dependent Downloads while automatic installation is off. The original error remains unchanged in both list and details; direct-transfer failures get no update advice.

`tests/ui/video-updates.spec.ts` covers toast actions, repeat launch, a later version, Settings markers/progress, original error text and projected advice, with axe audits. `video_tools::tests::schedule` uses signed HTTP fixtures and a controllable clock to verify cadence, silence, preferences, ineligible states, retry, notification claims and cancellation.

## yt-dlp source selection in Opul Nightly

[The Nightly switch](video-tools-compatibility.md) uses this update path with explicit consent, including when automatic installation is off. A channel change can select an older version, cancels obsolete work, and clears source-specific metadata. Installed and rollback pairs retain channel identity; scripts from stable and nightly have different version directories. Availability notification identities include the source channel.
