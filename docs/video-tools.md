# Video tools

Issues #61 and #62 supply verified setup from Settings and recovery through interrupted connections and restarts. Direct files and torrents need no video tools. Python, curl_cffi and sandboxed QuickJS are one Opul runtime; the official bare yt-dlp script is the other part. They become usable together after verification and a health check.

## Public interface

`opul_core::video_tools::VideoTools` owns installation, selection and preferences. The shell opens it with `VideoToolsConfig { root, opul_version, built_in_tools }`. `root` is the channel-resolved Application Support directory plus `Tools`, including any `OPUL_DATA_DIR` override. Stable and Nightly each construct a separate instance. Both currently use stable yt-dlp.

- `snapshot()` reads `VideoToolsSnapshot`; `subscribe()` returns a watch receiver with the current value and pushed changes. `sequence` increases within a module instance. Slow receivers may coalesce progress. Register listeners before reading, and reject older sequence numbers within that instance.
- `execute(operation)` accepts `SetUp`, `Retry`, `CancelSetup`, `TurnOff`, `SetKeepUpToDate { enabled }`, and `RefreshPublishedSize`. It returns the current snapshot. Setup runs in the background. Duplicate setup commands during setup or Ready do nothing. Preferences commit before the command returns. Retry and Setup both express consent, including from Turned off.
- `invocation()` returns a `VideoToolsInvocation` only in Ready. It supplies the interpreter, bare script, QuickJS and built-in tools directory. MediaEngine reads this dynamically before probes and when constructing a transfer worker. Each worker retains its selected command for that transfer. Paths never cross the frontend bridge.
- `diagnostics()` includes the state, detailed error, installed versions, resolved candidate runtime/yt-dlp versions when available, chip and Opul version for Copy details.

The snapshot has exactly one `state`: `not_set_up`, `turned_off`, `setting_up`, `ready`, or `not_working`. It also carries `keep_up_to_date` and nullable `published_size`. Setting up has Python and yt-dlp steps, with `pending`, `waiting_for_internet`, `downloading`, `verifying`, `installing`, `done`, or `failed`, downloaded bytes and nullable total bytes. A failed initial setup becomes Not working with a download, verification or health-check reason. Missing or unlaunchable installed files become Not working with `stopped_working` at restart.

Ready carries the runtime number, Python version, yt-dlp version, nullable `last_checked` Unix timestamp and exactly one update flag: `none`, `available { version }`, `updating { version, progress }`, `failed { version }`, or `waiting_for_runtime { version }`. This slice activates with `none`; it defines and renders the other flags for #65. An update must preserve Ready and its selected pair until another candidate passes verification and health checks.

Tauri exposes `tools_snapshot` with `{ video, built_in: { ffmpeg, ffprobe } }`, `video_tools_execute`, `video_tools_details`, and pushed `video-tools` events. Settings subscribes before its initial read. Tools controls commit immediately and do not participate in the other Settings sections' draft or Save flow. Settings requests published metadata when Not set up; this fetches the signed pointer, the release tag and signed checksum metadata, then HEADs the script for its size. It never fetches executable payloads or grants consent. Failed metadata lookup leaves the `about 23 MB` fallback. Opening the module itself performs no network request.

## Waiting Downloads

Video submission stores an unprobed `PendingPage` in the application checkpoint before extraction. The accepted Download retains its identity, Workspace, Saved Folder, format, source URL and media policy. When tools are unavailable the reducer uses `WaitingForVideoTools`, with no transfer effect. Direct files and torrents continue through their existing paths.

The application observes the managed tools snapshot before reconciliation, before accepting a video page or retry, and in the effect runner. It checkpoints availability changes as facts. Ready queues waiting rows and creates ordinary `EnsureTransfer` effects. Repeated Ready facts create no extra effects. Reconciliation fences these starts across restart, including when Ready arrives before the session becomes Running. The default Ready availability is omitted from checkpoints to preserve older checkpoint checksums and supports core callers without a managed-tools module; the desktop always supplies its manager before starting the runner.

An `EnsureTransfer` for a pending page probes only after it is queued. A dedicated worker serializes probes while the ordinary runner continues download controls and adapter observations. The subprocess drains stdout and stderr concurrently, has a two-minute deadline, and is killed when the accepted attempt, generation or session no longer permits it. Pause before a transfer exists records Paused immediately; resume can probe again. Shutdown stops the probe worker before joining the runner. Its resolved fact replaces the pending row at the same position, gives the first unique playlist entry the original identity, and inserts later entries in playlist order. It skips URLs already present in that Workspace. Other Workspaces have independent deduplication. The saved folder, format and policy apply to every accepted entry. A stale or repeated result cannot expand a cancelled, retried or already resolved page.

The projection provides the waiting label and `can_set_up_video_tools` / `can_retry_video_tools` capabilities. Not working shows "Video tools aren't working" with Try again; Turned off shows "Needs video tools" with Set up. Frontend rows use these capabilities directly. Cancelling and removing waiting rows remain available.

Submission in Not set up asks for consent with the published size or fallback. Download first saves the waiting row, then starts setup. A rejected add never starts setup. Not now, Esc and closing the dialog drop the pending submission; Don't show this again with dismissal persists Turned off. While Setting up, submissions need no second prompt. Turned off disables Video in type controls with the Settings explanation and suppresses submission offers. Explicit Set up from an existing waiting row is consent to re-enable tools.

Removal and returning already running transfers to waiting remain #66's responsibility. Use the waiting lifecycle and existing projected recovery capabilities when implementing that operation.

## Verification and pairing

1. Fetch the fixed Opul pointer and its raw Ed25519 signature. Verify exact JSON bytes before parsing. Retry a mismatched pointer/signature pair once, since publication replaces two assets.
2. Enforce schema 1, the minimum Opul version and the host architecture. Runtime URLs must belong to that runtime's immutable numbered release. Runtime 1 requires Opul 0.2.2; older development builds reject setup with an update explanation.
3. Resolve yt-dlp's HTTPS `releases/latest` redirect once. Fetch `SHA2-256SUMS`, its detached OpenPGP signature, and the bare script from that resolved tag. Verify the manifest with the embedded yt-dlp key before reading its script checksum. Never fetch a key beside the payload.
4. Stage the runtime archive under a unique `.install-<uuid>` directory. Verify its Opul signature before SHA-256 and exact size, then unpack with bounded expanded size and path/link containment checks. Verify the script checksum against the authenticated manifest. A signature/checksum failure discards that payload and retries it once; a second failure never executes or selects it.
5. Run the candidate interpreter with `-I`, its script, `--ignore-config`, `--no-plugin-dirs`, `--no-cache-dir`, `--no-update`, Chrome impersonation through the bundled curl_cffi handler, explicit sandboxed QuickJS, and explicit bundled FFmpeg/ffprobe directory. `--version` must report the exact resolved tag. A separate network-free `--verbose --list-impersonate-targets` invocation must report that version, a Python version, supported curl_cffi and QuickJS, and no Python deprecation warning. Both subprocesses have timeouts and are killed if setup is cancelled. `--version` alone exits before initializing the handlers, so it cannot establish compatibility.
6. Move both verified parts into their version directories, then atomically replace `state.json`. Only the committed selection becomes Ready. A cancelled operation cannot commit after a newer command.

The Opul raw Ed25519 trust anchor is embedded in `install.rs` and corresponds to `tools/python-runtime/signing-public.pem`. The yt-dlp OpenPGP trust anchor is embedded from `src/video_tools/keys/yt-dlp.asc`, retrieved from [yt-dlp's public key](https://github.com/yt-dlp/yt-dlp/blob/master/public.key). [yt-dlp's installation documentation](https://github.com/yt-dlp/yt-dlp#release-files) specifies OpenPGP checksum signatures. Its key format differs from Opul's raw detached signatures. Fixture tests generate independent test keys for both projects.

## Interrupted connections

All setup HTTP requests, including signed metadata and release resolution, retry transient connection/body errors, HTTP 408/429 and server errors three times after 2, 10 and 30 seconds. Other HTTP errors fail immediately. Interrupted bodies retain their received prefix and request `Range: bytes=<offset>-` with identity encoding. A 206 must describe the requested offset, a consistent total and a matching response length. If the server ignores Range and sends 200, the prefix is discarded and the response starts a fresh file. Signature and checksum verification still cover the entire recovered payload before any execution. A verification failure discards the payload and downloads one fresh copy; a second failure enters Not working.

`NetworkEnvironment` injects reachability and cancellable sleeps through `open_with_environment`; the default uses macOS SystemConfiguration reachability through `/usr/sbin/scutil -r github.com` and Tokio timing. Consented setup requests pause with `waiting_for_internet`, rendered as "Waiting for an internet connection…", keeping the displayed progress. Reachability is checked once a second while waiting. Offline waiting spends no retry attempts; reconnection continues automatically, including after a connection drops during backoff. An optional published-size lookup fails promptly while offline, retains the fallback, and releases its directory lock. Reachability service errors fall back to normal bounded HTTP retries. An absent route is offline; a reachable server returning errors remains a download failure.

Resume applies within an active setup operation. Cancel and restart discard temporary payloads and require explicit consent to start setup again. They never resume or execute an abandoned candidate. No payload is exposed to MediaEngine until both parts are verified, health-checked and selected by state.json.

## Storage and lifetime

`Tools/state.json` stores the selected `installed` pair, `previous_runtime`, `previous_yt_dlp`, the full `rollback_pair`, `last_checked`, `compatibility_hold`, integrity skips, `keep_up_to_date` and `turned_off`. New fields default for older state files. The updater records and releases retention references; startup preserves the selected pair and these explicit predecessors, and prunes all other version directories. If state.json cannot be parsed, startup reports stopped-working and preserves version directories for repair. Installed files live at `python-runtime/<number>/` and `yt-dlp/<tag>/yt-dlp`. The shell's channel resolver chooses `Application Support/Opul` or `Application Support/Opul Nightly`, or the exact `OPUL_DATA_DIR` override. A file lock prevents multiple module instances from writing one Tools root. Setup excludes Tools from Time Machine with the system `tmutil` before downloading. Failed or cancelled staging directories are removed. Opening the module removes stale `.install-*` directories and unfinished `.state-*.json` writes while holding the exclusive tools lock. Missing, non-executable or unlaunchable selected files enter Not working with the stopped-working reason; Retry replaces them through verified setup. The shell cancels any tools operation before its shutdown checkpoint. Cancellation never changes the committed selection.

A failed candidate leaves the committed selection unchanged. Turn off is the initial suppression choice, not removal of an active Ready pair. Removal, including stopping transfers and optionally turning off, belongs to #66. `OPUL_YT_DLP` is the sole hidden developer override. It bypasses managed command selection, never appears in Settings, and is rejected by the managed-tools smoke harness. Homebrew, PATH discovery, path preferences and the legacy tool-status API are gone.

## Verification

`cargo test -p opul_core video_tools` drives public commands against local HTTP fixtures with generated Ed25519/OpenPGP keys and a fixture interpreter. It checks consent and restart preferences, tampered metadata/payloads before execution, minimum app version, accepted/rejected health checks, cancellation, committed selection, restart validation and the arguments actually supplied to an already-open MediaEngine. `vp run test tests/ui/video-tools.spec.ts tests/ui/built-in-tools.spec.ts` exercises the mocked desktop bridge, pushed snapshots, immediate preferences, all initial states, Ready flags and axe audits.

For a real packaged check, build an app with version at least 0.2.2, then run `Scripts/smoke_video_tools.sh <app-path>`. It launches that app with isolated data/download directories, expresses consent through the module, verifies published assets, probes and downloads the permitted W3C sample through the real application state machine and MediaEngine, records versions and output size, and checks Time Machine exclusion. This test uses the network and is separate from normal CI.

## First-launch Setup

Setup fills the app window as a modal view. It leaves macOS's window mode alone. The desktop preference `video_tools_setup_shown` records the first offer with an atomic, immediate write, outside the Settings draft. Settings saves preserve the live flag. Not now, Esc and the close button dismiss the view without installing. Don't show this again uses the module's Turn off command before dismissing. Already Ready or Turned off installations receive no automatic offer.

Help ▸ Set Up Video Tools… and Settings ▸ Tools ▸ Set Up Video Tools… reopen the same view. Opening it grants no install consent. Download and Try again use the existing module operations, and the update checkbox writes the existing immediate preference. Setup and Settings share `VideoToolsProgress` and pushed snapshots. Continue to Opul closes only the view; the module continues installing. While Setting up, the sidebar shows the mean of the two steps' download progress, counting finished steps as complete and unknown-size steps as pending. Clicking it reopens Setup. A transition from Setting up to Ready removes the sidebar line and emits one ready toast. Opening an already Ready app emits no ready toast.

`tests/ui/video-setup.spec.ts` covers first launch, consent and each dismissal, repeat launch, Help and Settings re-entry, live steps, sidebar re-entry, completion, and direct-file and torrent submission during setup. Axe audits cover the offer and progress views. The desktop preference test reopens the real store and checks that stale Settings cannot restore the offer. Installation, retries and verified payload ownership remain in the video-tools module.

## Removing video tools

The desktop Remove operation goes through `OpulStateMachine::remove_video_tools`. The tools manager revokes selection and cancels the current job under the activation lock. The application checkpoints every unfinished video Download as waiting with a new attempt and control generation, invalidating late process and probe results. The effect runner cannot enqueue transfers during removal. Video process groups stop and exit before managed files are pruned. Direct transfers, torrents, finished output and partial files are retained.

Removal persists an empty installed selection and preserves the update preference and any existing Turned off choice. Explicit setup restores waiting Downloads through the normal Ready transition. Setup and update activation share the cancellation lock, so an obsolete job cannot select tools after removal. Other Stable/Nightly tool roots are untouched. If a writer does not exit, removal reports an error and retains its files until it exits; Remove can be retried.

Tool-dependent Guided conversions are marked in the persisted origin and projection; original direct Guided transfers remain independent. In-memory Guided credentials are kept for removal/re-setup within the session, released for terminal Downloads, and cleared under the execution gate by Clear browser login data. As with other Guided restarts, credentials are not checkpointed.

A transition to unavailable tools also checkpoints unfinished dependent Downloads as waiting. This repairs an interrupted removal where tool state was saved before the Download checkpoint. Repeated unavailable snapshots leave subsequent person controls alone. Removal errors publish Not working with details, keeping Remove available for another cleanup attempt.
